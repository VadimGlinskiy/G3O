1. THE CORE CHALLENGE: RETROFITTING MULTITHREADING INTO A 2006 SINGLE-THREADED ENGINE
==============================================================================

Gothic 3 was built by Piranha Bytes between 2003 and 2006. The Genome Engine was
architected strictly around a single main execution thread (the Win32 message pump
and engine tick loop in Gothic3.exe).

On modern PCs with 16–24 hardware threads and NVMe drives (>1,000 MB/s), loading a
saved game takes ~31.0 seconds. 19+ CPU cores sit at 0% utilization while the main
thread churns through single-threaded decompression, reflection, and object creation.

------------------------------------------------------------------------------

------------------------------------------------------------------------------
1. PAK Decompression in GotoLoadedPosition:  9.672 s (31.2%) -> Main thread zlib/deflate
2. Dynamic Layer Parsing (SysDyn):           6.014 s (19.4%) -> Main thread property deserialization
3. Scene & Entity Setup (D3D9/PhysX):        6.207 s (20.0%) -> Vertex buffers, textures, PhysX actors
4. Other Dynamic Layers (344 layers):        2.602 s ( 8.4%) -> World/mod layer deserialization
5. Savegame Deserialization (LoadGameWorld): 2.081 s ( 6.7%) -> Savegame chunks
6. Disk ReadFile I/O:                        1.787 s ( 5.8%) -> 1,931 MB read at 1,081 MB/s (NVMe NOT bottleneck!)
7. Overhead / PVS / Node Expansions:         1.511 s ( 4.9%)

------------------------------------------------------------------------------
The "Graveyard of Disasters" — Invariants That Must NEVER Be Violated:
------------------------------------------------------------------------------
1. 32-bit Virtual Address Space (VAS) Limit:
   Total uncompressed PAK assets in GotoLoadedPosition = 2,930 MB. Total VAS ceiling is ~3.5 GB.
   Holding all decompressed data simultaneously triggers an instant Out-Of-Memory Guru crash.
   All background buffers MUST be bounded (e.g., G3O's StaticBoundedSlabArena capped at 88 MB).

2. Ground Clamping & gCNavigationAdmin::Process():
   Skipping or rate-limiting navigation ticks during load causes creatures to spawn under the
   terrain and vertically snap upwards ("creature vertical teleportation").
   RULE: NEVER hook, skip, or throttle gCNavigationAdmin::Process().

3. Property Stream Cursor Integrity (bCIStream):
   Altering the stream cursor (e.g., pre-reading header bytes) breaks bTPropertyObject::ReadData,
   causing "illegal propertyobject version detected. Filebounds exceeded?" crashes.
   RULE: NEVER corrupt or advance bCIStream cursors during property reading.

4. No Negative Caching Across Sectors:
   Entities load across sector boundaries lazily. Caching nullptr for missing templates causes
   quest NPCs and items to permanently vanish.
   RULE: Only positive caching or epoch-based invalidation is allowed.

5. gCInfoManager Dialogue State:
   Caching or skipping dialogue condition queries breaks NPC dialogue trees and merchant trade
   options ("Show me your wares").
   RULE: Dialogue evaluation must run via vanilla logic.

  0x100C5B04: mov ecx, eax                          -> this = gCWorld*
  0x100C5B06: call 0x1019C420                       -> gCWorld::OnLoadDynamicContext(stream, layer, flag)

Why Direct Multithreading Crashes Inside DoLoadData:
1. Global String Admin (g_pStringAdmin / bCString):
   bCString uses non-atomic reference counting (add dword ptr [eax-4], 1).
   Concurrent string copies or destructions corrupt the reference counts, triggering double-free
   or heap corruption.
2. Property Object Reflection Singletons:
   bCPropertyObjectFactory::ReadNewObject (SharedBase.dll+0x59330) and
   bCPropertyObjectSingleton::ReadNewObject (SharedBase.dll+0x5BE50) mutate shared global
   registries and cache structures without synchronization.
3. Scene Administration (eCSceneAdmin):
   Inside OnLoadDynamicContext, each entity registers its GUID (bCPropertyID) into
   eCSceneAdmin::m_templateMap (a hash map with only 43 buckets).
   Concurrent insertions corrupt the bucket linked list pointers, causing infinite loops or Guru crashes.
4. Scene Graph Linking (eCNode::AttachChild):
   Entities are attached to the sector's root node. Without locks, concurrent node attachment corrupts
   the parent-child array.

3. ARCHITECTURAL PATTERNS FOR "INDIRECT" MULTITHREADING IN GOTHIC 3
==============================================================================

If direct multithreading of legacy engine functions is impossible due to non-thread-safe
singletons, how can concurrency be achieved "indirectly"?

Here are the 4 fundamental patterns that can be applied to Gothic 3:

------------------------------------------------------------------------------
PATTERN 1: Decoupled Asynchronous I/O & Decompression Staging (Producer-Consumer)
------------------------------------------------------------------------------
Concept:
The engine's load routines combine 3 distinct phases into one synchronous loop:
  [Disk Read] -> [Zlib Decompress] -> [Engine Object Deserialization]
Pattern 1 strips out the first two phases (Disk Read + Decompress) and executes them on
a pool of background worker threads ahead of time.

Application to DoLoadData:
- All 345 dynamic layers correspond to .lrentdat files stored in Projects_compiled.* archives.
- At the beginning of gCWorld::Activate, background workers scan the archive FAT table and
  pre-decompress all 345 .lrentdat streams into memory buffers (e.g., using G3O's
  DynamicLayerOptimizer or StaticBoundedSlabArena).
- When the main thread calls gCDynamicLayer::DoLoadData sequentially, the stream is already
  100% in RAM! The main thread incurs 0 ms disk wait and 0 ms decompression time.

Application to GotoLoadedPosition:
- Implemented in G3O via src/static_slab_arena.h and src/pak_tracer.cpp:
  8 worker threads decompress up to 64 blocks ahead into an 88 MB static slab arena.
  Main thread Hook_ZlibDecompress performs an instant 0.04 ms memcpy into the engine buffer.

------------------------------------------------------------------------------
PATTERN 2: Two-Phase "Isolated Worker Parse -> Serial Main-Thread Commit" (ECS Batching)
------------------------------------------------------------------------------
Concept:
Separate the computationally expensive parsing of raw bytes from the registration of
engine objects.

Phase A (Worker Threads, Highly Parallel):
- Workers read the binary .lrentdat / .node stream.
- Workers parse raw integers, floats, vectors, GUIDs, and byte buffers into thread-local,
  isolated C++ POD structs (e.g., struct RawEntityRecord { GUID id; Matrix4x4 transform; ... }).
- Workers do NOT instantiate eCEntity, do NOT touch bCString, and do NOT touch eCSceneAdmin.
- Because workers only manipulate private heap/stack memory, 16+ cores can parse streams in parallel
  with 0 contention.

Phase B (Main Thread, Serial & Ultra-Fast):
- The main thread iterates over the pre-parsed, in-memory RawEntityRecord arrays.
- It calls eCEntity constructors and eCSceneAdmin registration in a tight, sequential loop.
- Because all string parsing, byte unmarshaling, and endian swaps were already done by workers,
  main-thread execution time drops by 60–75%.

------------------------------------------------------------------------------
PATTERN 3: Bypassing Legacy Heap Locks via Thread-Local Allocators (mimalloc)
------------------------------------------------------------------------------
Concept:
In SysDyn, over 100,000 property objects perform millions of small allocations via
bCMemoryAdmin (SharedBase.dll+0xC9E0 / 0xC8E0).
In vanilla Genome, bCMemoryAdmin acquires an internal critical section / lock on every
allocation and walks single-threaded freelists.

Solution in G3O:
- Implemented in src/memory_allocator.cpp (AllocatorMode=2: Full MemHeap Replacement).
- Uses mimalloc 3.5.3 with thread-local lock-free pages, O(1) size classes, and a
  Zombie-Safe Header with canary (0x47334F21) and a 65,536-entry quarantine ring to prevent
  ABA reuse races.
- Cuts CPU overhead of property allocation during SysDyn by ~35% directly on the main thread
  without touching bCIStream.

------------------------------------------------------------------------------
PATTERN 4: Speculative Asset & Physics Pre-Cooking
------------------------------------------------------------------------------
Concept:
In GotoLoadedPosition, 6.207 seconds are spent in Scene & Entity Setup:
- Creating PhysX 2.x collision objects (Engine.dll!?CreatePhysicObject@eCEntity@@QAEXXZ at 0x225750,
  Engine.dll!?AddPhysicObject@eCPhysicsScene@@IAEXPAVeCPhysicObject@@@Z at 0x171400).
- Cooking collision triangle/convex meshes (NxCookingInterface) from .xcom / .xshm files.
- Creating Direct3D 9 vertex/index buffers and textures (Engine.dll!eCDX9Device at 0x9B810 / 0x9B930).

How to parallelize:
- While PhysX NxScene::createActor must remain on the main thread, the cooking of collision meshes
  (transforming raw vertices/indices into PhysX internal formats) is a pure mathematical calculation!
- Worker threads can pre-cook triangle and convex meshes in background threads into memory buffers.
- When the main thread instantiates the entity, it uses the pre-cooked PhysX descriptor, turning a
  5 ms cooking operation into a 0.01 ms pointer registration.
